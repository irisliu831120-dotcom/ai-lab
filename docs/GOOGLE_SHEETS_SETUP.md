# 山餃：Google 試算表訂單串接

狀態：前端、GAS 與本機測試完成；原生 Google 試算表已建立於 Google Drive 的 ChatGPT 資料夾，只有擁有者可存取。前端預設 `mode: 'test'`，但 GAS endpoint 留空。在 Google 授權部署完成前，網站仍為不傳送資料的模擬結帳。尚未完成 GAS 部署與雲端端對端測試。

## 已確認的需求

- 新建「山餃訂單管理」Google 試算表。
- 先做測試串接，不接真實訂單、不收款、不安排出餐。
- 保留既有 GitHub Pages、PWA、購物車、首頁動畫及 Google Calendar 預約。

## 資料流程

1. 顧客在網站填寫測試資料並同意傳送。
2. 前端用隱藏表單將 POST 送往 GAS `/exec`，資料放在 POST body，不放 URL。
3. GAS 驗證商品 ID、數量、價格、門市、取餐方式與同意欄位，以後端價格計算總額。
4. 在 ScriptLock 內，使用請求識別碼檢查是否已有訂單；相同內容回傳原單號，不新增第二列。
5. 以一列寫入訂單、金額與聯絡欄位，完成後回傳不含個資的收據。
6. GAS HTML 回覆以 `postMessage` 回傳給網站；前端驗證 Google 來源、單次隨機 nonce、請求識別碼、金額及模式。
7. 只有有效成功收據才清空已送商品。逾時／錯誤保留購物車及同一個重試識別碼。

這個流程處理 GAS 與 GitHub Pages 跨來源的限制。沒有使用 `fetch(...,{mode:'no-cors'})` 將不透明回應誤當成成功；沒有把 Google OAuth token 或私人金鑰放在網站。

## 一次性 Google 設定

需要由試算表擁有者使用自己的 Google 帳號授權；本專案不含任何帳號憑證。

1. 開啟本次建立的「山餃訂單管理」試算表，選擇「擴充功能」→「Apps Script」，將綁定專案命名為「山餃訂單接收」。
2. 將本 repository 的 `gas/Code.gs` 完整貼入 GAS 的 `Code.gs`。
3. 在專案設定啟用顯示 `appsscript.json`；將 `gas/appsscript.json` 的內容貼入對應檔案。此專案只要求試算表權限，不要求 Gmail 或 Drive 全域權限。
4. 在編輯器選擇 `setup` 執行並完成 Google 授權。它會沿用這份綁定的試算表、檢查「訂單」分頁，將 ID 留在 GAS 指令碼屬性。再次執行會沿用同一份試算表；若使用未綁定的獨立 GAS 專案，才會新建試算表。
5. 執行記錄會顯示試算表網址；保留這個網址。確認分享設定仍為受限制，僅加入需要處理訂單的管理者。
6. 選擇「部署」→「新增部署作業」→「網頁應用程式」；執行身分選「我」，誰可以存取選「所有人」。這只公開接收端，不會公開試算表。如帳號政策不允許匿名網頁應用程式，停止部署並改用可驗證身分的後端，勿公開試算表來繞過限制。
7. 複製部署完成的 `https://script.google.com/macros/s/部署識別碼/exec` 網址，勿使用 `/dev`。
8. 將此 `/exec` 網址交給協作助手，或自行填入 `checkout-config.js` 的 `endpoint`。保留 `mode: 'test'`。
9. 每次修改網站端的設定或程式時，增加 `sw.js` 的快取版本，提交並等待 GitHub Pages 部署成功。已開啟的 PWA 需要關閉所有該網站分頁／App 後重開，才能切換至新 Service Worker。

**完成 Google 部署後只需要提供：GAS `/exec` 網址；試算表已建立並確認。** 連接 Google Drive 可以協助管理試算表，但不代表已取得 Apps Script 的授權或部署權限。

| 屬性 | 預設／用途 |

## 試算表欄位

| 欄位 | 說明 |
| --- | --- |
| 訂單編號／建立時間 | 測試單以 `TEST-` 開頭，時間使用 Asia/Taipei |
| 請求識別碼／內容指紋 | 重試去重；勿手動修改 |
| 模式／處理狀態 | `test`、`測試／不履約` |
| 姓名／電話／電子郵件 | 測試聯絡資料；電話保留前導零 |
| 取餐方式／門市／宅配地址 | 內用、外帶或冷凍宅配 |
| 商品明細 | 商品名、份數與單價 |
| 商品小計／運費／總額 | 後端計算；冷凍宅配運費 NT$160 |
| 付款狀態／備註 | 預設「未付款」；管理者備註 |

商品明細與訂單寫在同一列，避免多分頁寫入一半造成不完整訂單。聯絡資料以文字寫入，避免試算表公式注入。請不要重新命名或移動既有標題；可在最後一欄右側加入管理用欄位。

## 雲端驗收步驟

請使用虛構資訊，例如姓名「測試顧客」、電話 `0900000000`、信箱 `test@example.com`。Google 回覆只回傳收據，不包含顧客姓名、電話或地址。

- 開啟 GAS `/exec`：應顯示 `{"service":"shan-jiao-orders","ok":true,"version":1}`，不應看到登入畫面或權限錯誤。這只確認服務存在，不代表 Sheets 寫入已通過。
- 網站購買原味鍋貼 2 份外帶：後端總額應為 170，Sheet 新增一列，付款狀態為未付款。
- 冷凍禮盒 2 盒宅配：應為 900+160=1060。
- 有現煎商品時不應提供宅配；冷凍商品不應提供內用。
- 送出時按鈕停用；成功回覆前不應清空購物車。
- 模擬斷線或回覆逾時：不應顯示成功；在同一分頁、相同資料重試時應返回原單，Sheet 不應多一列。請勿在結果不明時另開新單或更改資料。
- 直接修改請求金額：後端應拒絕；相同識別碼搭配不同內容也應拒絕。
- 以 iPhone Safari 與 Android Chrome 各測一次，確認第三方 iframe 回覆可以抵達。如果受瀏覽器或 Google 帳號政策阻擋，停留在測試模式並改評估同源伺服器代理；不能把逾時視為成功。
- 確認試算表沒有公開，且未在 console 記錄顧客表單內容。

## 管理與後續擴充

這階段 GAS 提供建表、資料驗證、後端計價、寫入、鎖定與去重；管理者可在 Sheet 人工處理狀態。尚未做付款、庫存扣減、通知郵件／LINE、配送或自動履約，不會主動傳送通知。

公開 GAS URL 是接收地址，不是秘密或買家身分驗證。現有每支電話每分鐘三筆的新單限制只屬盡力節流，無法阻止分散式濫用；若開始正式營運或流量增加，需評估伺服器端驗證、CAPTCHA、配額監控與訂單保留期限。請求識別碼只在當前瀏覽器分頁保留 24 小時，無法替跨裝置重下單去重。

正式上線前需另外確認真實商品、價格、門市、營運狀態、個資告知與保留政策。之後才一起變更前端 `mode: 'live'`、GAS `ACCEPT_LIVE_ORDERS: 'true'`，並更新目前明示為測試的文字，不能只改一個開關。

## 開發驗證

```sh
node --test tests/orders.test.cjs
node --check checkout.js
node --check checkout-config.js
node --check sw.js
node --check < gas/Code.gs
```

目前七組 Node 測試通過，包含後端計價、取餐規則、去重衝突、公式注入、節流、鎖定、GAS 回覆消毒、訊息來源驗證、逾時重試、離線拒絕送單，以及初始化沿用綁定試算表。這些是模擬測試，不取代實際 Google 服務與手機端對端驗收。
